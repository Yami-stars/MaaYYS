## 2. schema 校验器

`InterfaceConfig.Load` 只保留 4 项「不过就没法继续」的硬校验（interface_version、controller
类型、import 存在性、option 引用），其余全部进了 `InterfaceSchemaValidator`，可以单独跑：

```powershell
MaaYys.P1Probe.exe pi --validate resource/interface.json
```

三级结论：

| 级别 | 含义 | 当前清单上的结果 |
|---|---|---|
| **Error** | 协议不合法 / 引用悬空 / 路径不存在 | **0** |
| **Warning** | 能跑但值得看一眼 | 1（见下） |
| **Info** | 统计 | 控制器 3 · 资源集 8 · 任务 29（顶层 0 + import 29）· 选项 94 · 分组 3 · import 29/29 |

校验覆盖：

- **必填与类型**：`interface_version=2`、`name`、controller/resource/task 非空、name 唯一、
  `type` 属于 Schema 枚举、option 类型合法、select/switch/checkbox 必须有 cases、
  input 必须有 inputs、`default_case` 必须指向存在的 case；
- **跨段引用**：`task.group` / `task.controller` / `task.resource` / `resource.controller` /
  `case.option` 指向必须存在；定义了却没有任务用的分组给 Warning；
- **路径存在性**：`resource[].path`、`attach_resource_path`、`icon` / `welcome` / `license`、
  `agent.child_exec`（agent 未接之前给 Warning 不给 Error）；
- **Win32 参数**：`window_regex` 与 `class_regex` 至少要有一个；
  **键鼠/截图方式写错名字直接报 Error** —— MaaFramework 对未知名字是<b>静默回退</b>
  （截图落到 PrintWindow、输入落到 SendMessage），不拦就会悄悄改变行为；
  `PrintWindow` 额外给 Warning（P1.4 实测：DPI 缩放下黑边导致点击整体偏移）。

当前清单仅剩的一条 Warning 是 `controller[Android].adb` 未声明 adb 段 —— 用框架默认能力探测，符合预期。

## 3. Win32 参数可配置化（补上的一块）

**之前的问题**：`controller[].win32` 段被解析出来只是打印，真正连控制器用的是代码常量
（FramePool + SendMessage）——改清单不生效。

现在的规则（**清单 = 默认值，实例 = 覆盖**）：

| 参数 | 来源优先级 |
|---|---|
| 窗口标题/类名正则 | 实例字段（实例页可编辑）→ **为空时**回落 `win32.window_regex` / `class_regex` |
| 截图方式 | 实例 `screencap_method` → 为空时回落 `win32.screencap` |
| 输入方式 | 实例 `input_method` → 为空时回落 `win32.mouse`（keyboard 同取） |

新建实例的草稿也会用清单默认值预填，所以用户在实例页看到的就是清单里的值，改了就按实例的走。

### 顺手修掉的一个配置/行为不一致

校验器第一条 Warning 抓到的就是它：MXU 原清单写的是 `"screencap": "PrintWindow"`，
而我们的引擎实际用的是 **FramePool**（P1.4 实测 PrintWindow 在 DPI 125% 下黑边约 20%、
点击整体偏移；FramePool 无此问题）。P3.6 之前这属于「清单写着 A、程序做着 B」；
P3.6 之后清单变成权威，若不改就会**回退**成 PrintWindow。

→ 已把 `resource/interface.json` 的 `win32.screencap` 从 `PrintWindow` 改为 `FramePool`，
让配置与实测结论一致。这是本次对清单唯一的实质修改。
