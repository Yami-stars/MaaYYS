# 缓存清理与资源整理

> 日期：2026-10-26（第二版，按「一个按钮 + 版本更新自动整理」重做）
> 代码：`MaaYys.Engine/Cleanup/`（`ImageCache` / `ResourceAudit` / `ResourcePruner` / `ResourceMaintenance`）、`MaaYys.App`（设置页）
> 工具：`MaaYys.P1Probe.exe audit [...]`、`MaaYys.P1Probe.exe cache [...]`

## 1. 最终形态

| 用户看到的东西 | 行为 |
|---|---|
| 设置页一个按钮 **「清理图片缓存」** | 弹确认框 → 直接删掉 `debug/`、`cache/` 下的图片 → 显示「已删除 N 张，释放 X MB」。日志不删 |
| 设置页一块只读的 **「资源整理」** | 显示上次整理的时间 / 资源版本 / 删了多少。用户不需要点任何东西 |

两件事的分工是**刻意的**：

- **图片缓存**是运行时产物，删错了最多丢几张截图 → 交给用户手动，给个按钮。
- **过期资源**（不可达节点、未引用模板/模型、`*.bak`）是版本迭代的必然副产物，任何时刻都是垃圾 → 版本更新时自动清，不让用户做选择题。

## 2. 三个隐藏任务（保持隐藏、受保护）

| 任务文件 | 任务名 | 入口节点 | 选项数 |
|---|---|---|---|
| `tasks/限时活动.json` | 限时活动-泛舟争流 | `限时活动-泛舟争流` | 1 |
| `tasks/活动-小超鬼王.json` | 活动爬塔-武道大会-修行合训 | `活动爬塔-武道大会-修行合训` | 2 |
| `tasks/自动业原火.json` | 自动业原火 | `业原火-开始业原火` | 3 |

它们的 pipeline 合计 **72 个节点**。P3.1 做过实验：把这三个文件补进 import，可达节点 1039 → 1111（+72），三份 pipeline 全部复活——说明**节点和链路都是好的，只是没接线**。

**以后怎么启用**：在 `interface.json` 的 `import` 数组里加一行即可，不需要改任何 pipeline：

```jsonc
"import": [
  "tasks/打开游戏.json",
  // …
  "tasks/限时活动.json"        // ← 加这一行
]
```

同一套方法适用于以后版本更新带来的新活动：活动包放进 `resource_pack/base/pipeline/活动/`，
任务声明放进 `tasks/`，**先不加 import**（隐藏），等自动整理的逻辑里它会被当作「受保护根」永远不动。

> 为什么不做 GUI 开关：任务可见性是 `interface.json`（PI V2 协议）的事，GUI 再存一份开关就是第二个真相来源。
> **资源清单说了算，界面只做提示。**

## 3. 按钮：清理图片缓存

范围只有一处：程序目录下的 `debug/` 与 `cache/` 里的**图片**（`.png/.jpg/.jpeg/.bmp/.webp/.gif/.tif/.tiff`），递归。

- **不删日志**（`*.log`）。日志是排查问题的唯一线索，用户点这个按钮的诉求是腾空间，不是抹现场。这一点和 MAA 的「清空图片缓存」一致。
- **不进回收区**。缓存是能重新生成的产物，恢复没有意义。
- 被占用的文件跳过并计数，不中断整体清理。
- 删完顺手收掉变空的子目录，`debug/` 不会留一堆空壳。

确认框文案（照 MAA 的口径，先讲清「正常情况下不用清」）：

```
确认删除所有图片缓存？

· 删除范围：debug、cache 目录下的全部图片（截图、调试用图）；
· 日志文件（*.log）会保留，排查问题需要的记录不受影响；
· 图片缓存会随运行重新生成，删除后部分界面需要重新截图，属正常现象。

注意：此操作直接删除，不进入回收站，删除后无法恢复。
```

## 4. 自动整理：资源版本更新时

### 触发条件

`config/resource-state.json` 记住上次整理时的 **`interface.json` 的 `version`** 与**资源指纹**
（`resource_pack/<bundle>/{pipeline,image,model}` 的文件数 + 总字节）。

- 版本号变了 → 整理；
- 版本号没变但资源被替换过（指纹变了）→ 也整理；
- 状态文件不存在（首次运行 / 换了资源包）→ 整理一次并落状态。

指纹是在**整理之后**取的，所以不会因为「文件变少了」在下次启动又触发一轮。

### 判定门槛：所有资源集都不可达才删

`interface.json` 有 8 个资源集（官服×3、bilibili、华为、应用宝、OPPO、VIVO）。某个节点在官服走不到、
在 bilibili 服有人用，它就绝不能删。所以整理对**每个资源集各扫一遍，取交集**：

- 项要在**每一套**里都是 `CanClean`；
- 节点级清理取**节点名交集**（每套都走不到的那些）。

### 删除范围

| 类别 | 处理 |
|---|---|
| 不可达节点（可达性遍历 + 锚点解析） | 删节点，重写 JSON |
| 整份都不可达的 pipeline 文件 | 删文件 |
| 未引用的模板图 / ONNX 模型 | 删文件（双保险：节点里没引用**且**文件名不在任何 pipeline 原文里） |
| 运行期配置备份 `*.bak` / `*.bad-*` | 删文件 |
| **受保护**：隐藏任务入口链、`活动/` 下轮换包、`debug.json`、`model/ocr/*` | 永不处理 |

### 为什么不做回收区

删的时机是「资源版本更新」，删掉的是**上一版资源包里**的东西——新版资源包自带自己需要的一切，
还原它们没有意义。回收区只会让用户目录里长期躺一份同样大小的副本，等于没清理。

安全底线不靠回收区，靠判定：

1. `CleanupRisk.Protected` 的项永不进入删除队列；
2. `interface.json` / `default_pipeline.json` / `debug.json` 硬编码禁止删除；
3. 只有解析后仍落在 bundle 目录**内部**的路径才会被动（拦 `../../` 越界）。

### 为什么必须循环到不动点

删掉死节点会让「只被这些死节点引用的模板图」变成新的未引用资源。所以一次整理要反复扫到没有变化为止
（上限 4 轮，实测 2 轮收敛）。只做一轮会留下 100 多张下一轮就没用了的图。

## 5. 实测（资源 v3.13.6，8 个资源集）

```
整理前：节点 1511（可达 1138 / 不可达 373）
  可清理 10 项 + 需确认 175 项 · 受保护 17 项 · 预计释放 22.1 MB

整理（一次调用，内部收敛）：
  删除 278 个文件、重写 9 个文件（清掉 214 个不可达节点），释放 23.2 MB

整理后：节点 1292（不可达 154）· 仍可整理 0 项 · 问题 0 条
  pipeline 自检：49 个文件解析成功、0 错误、0 悬空引用、模板图缺失 0
  资源体积：99 MB → 76 MB
```

剩下的 154 个不可达节点**全部是受保护项**（72 隐藏任务 + 82 轮换/兜底链）。也就是说，整理清掉的只有残骸，没有功能。

### 格式没有被破坏

节点级删除是**重写 JSON**，两个坑都处理了：

- **缩进**：从原文件第二行探测（本包是 2 空格），写回沿用；
- **行尾**：原文件是 CRLF，写回保持 CRLF、UTF-8 无 BOM。

实测 `日常/寮30.json` 1200 → 421 行，`diff` 里**只有删除行，没有一行被重排**。

## 6. 怎么用

### GUI

- **设置 → 图片缓存 → 清理图片缓存**：确认后立即执行，结果直接显示在按钮下方（`已删除 10 张图片，释放 10.2 MB`）。
- **设置 → 资源整理**：只读。首次启动（或版本更新后的首次启动）会自动整理，结果写 `debug/resource-prune.log`。

### 命令行

```powershell
MaaYys.P1Probe.exe audit                        # 只扫描，打印分组清单（只读）
MaaYys.P1Probe.exe audit --json out.json        # 扫描结果落 JSON
MaaYys.P1Probe.exe audit --prune                # 执行整理（多资源集取交集，直接删除）
MaaYys.P1Probe.exe audit --set "bilibili服" --no-assets   # 换资源集 / 跳过资产扫描
MaaYys.P1Probe.exe cache                        # 看图片缓存占用
MaaYys.P1Probe.exe cache --clear                # 清空图片缓存（= 界面按钮）
```

## 7. 刻意没做的事

| 没做 | 原因 |
|---|---|
| 删活动轮换包（9 份「活动300-*」+ 4 份限定） | 每月换一期活动，删了下次要从上游包里翻回来；「保留成本」低于「找回成本」 |
| 删 `model/ocr/*` | pipeline 里没有任何引用，但框架内置 OCR 按固定路径加载，删了 OCR 全废 |
| 把「哪些能删」做成界面勾选 | 那等于把必然正确的动作变成可能选错的选择题；判定留在引擎，界面只做展示 |
| 批量重命名 40 个不规范节点 | 改名要同步 800+ 处 `next` 引用，漏一处就是运行期静默断链；收益只是好看 |

## 8. 回归清单

```powershell
dotnet test tests/MaaYys.Engine.Tests     # 143 个用例（含 13 个缓存/整理用例）
MaaYys.P1Probe.exe audit                  # 期望：整理后「仍可整理 0 项」
MaaYys.P1Probe.exe audit --prune          # 期望：再跑一次「没有需要整理的过期资源」
MaaYys.P1Probe.exe pipeline               # 期望：0 错误、模板图缺失 0
```

测试锁住的语义：隐藏任务节点算活、活动包与 `debug.json` 受保护、OCR 模型受保护、配置备份可识别、
审计不修改任何文件、整理只认 `CanClean` 项、越界路径（把 `interface.json` 当死文件）被拒绝、
原缩进与行尾被保留、dry-run 不动任何文件、多资源集取交集（任一集保护即保护）、
版本未变不重复整理、版本变化后再次整理、图片缓存只删图不删日志。
