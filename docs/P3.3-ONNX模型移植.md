## 3. 两个必须记住的坑

**坑 1：`model` 字段只写文件名，但它不在 `model/` 根下**

节点里写的是 `"model": "BarrierCard.onnx"`，文件实际在 `model/detect/BarrierCard.onnx`。
框架会按文件名在 `model/` 下递归查找，所以能命中；**但任何自己写查找逻辑的工具
（如资源整理、缺失校验）都必须递归匹配，不能只在 `model/` 根下找** —— 否则会误判成缺失。

**坑 2：`model/ocr/*` 没有任何 pipeline 引用，但删了 OCR 全废**

`det.onnx` / `rec.onnx` / `keys.txt` 由框架内置 OCR 按固定路径加载，
pipeline 里根本不会出现它们的名字。P6.2 的资源整理已把 `model/ocr/` 加进受保护名单。

## 4. `model/` 整个目录已纳入受保护名单（2026-10-27 已处理）

P6.2 第一次「资源版本更新整理」曾把这两个当时无引用的模型删掉：

| 文件 | 体积 | 说明 |
|---|---|---|
| `model/detect/Courtyard-v5.0.onnx` | ~10 MB | 庭院皮肤 **v5** 的检测模型 |
| `model/detect/special-icon-v0.1.0.onnx` | ~10 MB | special-icon 的上一版 |

**处理结论：已恢复，并且保护范围从 `model/ocr/` 扩大到整个 `model/`。**

理由只有一条：**模型不可再生**。模板图删了能重截，模型删了只能重新训练或找回原文件；
而 `model/` 总共只有 6 个 `.onnx`、约 60 MB，全留着的代价远小于「以后要用时找不到」。
兼容性矩阵（流程表 8.2）里也明确要测「庭院皮肤 v5/v6」。

| 保护对象 | 理由（界面/探针里显示的就是这句） |
|---|---|
| `model/ocr/*` | 框架内置 OCR 直接按固定路径加载（pipeline 里不会出现引用），必须保留 |
| 其余 `model/**/*.onnx` | 模型不可再生（不像模板图能重截），即便当前无引用也保留，供以后换版本/换皮肤使用 |

模板图的策略**不变**（可再生 → 无引用仍会参与整理）。清理判定因此变成：
「模板图看有没有引用，模型一律不看」。

改动后复跑：模板图 435 张（未引用 0）、模型 10 个（未引用 0）、**受保护 23 项、可清理 0 项**；
`probe audit --prune` 连跑两次都是「没有需要整理的过期资源」（幂等）。
155/155 测试通过（两条模型相关用例已按新语义改写：无引用的 `detect/*.onnx` 从「需确认」变「受保护」、
整理后必须仍然存在）。

**后续约定**

1. 新增模型放 `model/detect/`，节点里 `model` 只写文件名（不带目录）。
2. 换模型版本时**不要直接删旧版**——先改 pipeline 引用，确认新版稳定后再考虑清理
   （模型不可再生，这是与模板图最大的区别）。
3. 任何模型缺失校验都要递归匹配文件名，不能按目录精确路径比对。
