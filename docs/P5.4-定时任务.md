## 二、数据模型

定时计划与配置组同级，存在 `config/maayys.json` 顶层 `timers` 数组（不进单个配置组，跨组共享）：

```json
{
  "config_version": 1,
  "current": "默认配置",
  "configurations": { "默认配置": { "name": "默认配置", "tasks": [] } },
  "timers": [
    {
      "id": "8f3c…",
      "label": "每日御魂",
      "hour": 8,
      "minute": 30,
      "configuration": "默认配置",
      "enabled": true,
      "weekdays": 126,
      "force_start": true,
      "last_fired": "202610270830"
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `id` | 实例唯一 Id，界面增删与去重用 |
| `label` | 备注名（可空），同点触发多条时区分 |
| `hour` / `minute` | 触发时刻，加载时夹取到 0-23 / 0-59 |
| `configuration` | 到点要运行的配置组名 |
| `enabled` | 是否启用 |
| `weekdays` | 周计划位掩码：**位索引 = `DayOfWeek` 数值**（0=周日 … 6=周六）。每天 = 127，工作日 = 62，周末 = 65 |
| `force_start` | 强制定时启动（见下） |
| `last_fired` | 最近触发的分钟键 `yyyyMMddHHmm`，**持久化**以保证「同一分钟内重启程序」不补触发 |

选 `DayOfWeek` 位序而不是 MAA 的 `0=周日/1=周一` 或 cron 的 `1=周一`，是为了让「存的值」和「.NET 枚举」一致——少一层换算就少一处出错可能。

## 三、调度核心

### TimerRules（纯函数，无状态）

| 函数 | 作用 |
|---|---|
| `ShouldFire(entry, now)` | 启用 + 时/分命中 + 星期命中 + 本分钟未触发过 |
| `NextOccurrence(entry, after)` | 严格晚于 `after` 的下一次触发（按天推进，最多找 8 天，O(8)） |
| `Normalize(entry)` | 夹取非法值；周计划为空时回落「每天」（避免永不触发的死配置） |
| `DescribeWeekdays(mask)` | 「每天 / 工作日 / 周末 / 一、三」 |

时钟全部由调用方传入，测试里直接 `Poll(固定时间)`，不需要真的等到 8:30。

### TimerScheduler

- 默认 **20 秒**轮询（1 分钟内至少检查 3 次，容忍系统休眠造成的 1~2 分钟漂移）
- 双重去重：**内存字典**（同一分钟不重复调用订阅方）+ **`last_fired` 落盘**（重启后不补跑）
- 订阅方异常被隔离，定时线程永不抛（一次写盘失败不该让后续周期停摆）
- `Poll()` 可单独调用：界面「立即检查」按钮与测试都走这条路径

## 四、执行接入

### 关键改动：执行入口提到 workspace 层

P5.3 时 `QueueExecutor` 归任务页所有。P5.4 必须解决一个问题：**定时到点那一刻，任务页可能根本没创建过**。若定时器自己再起一份执行器，两个队列会同时向 Maafw 投递任务。

所以新增 `Services/QueueRunService.cs`，挂在 `InstanceWorkspace` 上（全程序一份）：

```
TasksViewModel.RunQueueCommand ─┐
                                ├→ QueueRunService → QueueExecutor → MaaEngineExecutionHost → MaaYysEngine
TimerRunner（到点）─────────────┘
```

- 天然互斥：`RunAsync` 前检查 `IsBusy`，正在跑就抛「已有队列在运行」
- 引擎换了（切实例 / 重连）自动重建宿主，与 P5.3 逻辑一致
- 任务页退化为订阅者：只收 `ItemStatusChanged` 着色、收 `StateChanged` 刷新按钮，不再持有执行器

### TimerRunner

| 场景 | 行为 |
|---|---|
| 配置组不存在 | 报「绑定的配置组不存在，已跳过」，不启动 |
| 已有队列在跑 + `force_start = false` | 报「已跳过（未开启强制定时启动）」 |
| 已有队列在跑 + `force_start = true` | 先 `Stop()`，最多等 30 秒到空闲，再启动；超时报「旧队列 30 秒内未能停止」 |
| 引擎未连接 / 资源未加载 | `RunAsync` 抛 `InvalidOperationException`，报「启动失败：…」 |
| 正常启动 | 报「已启动配置组 X」，跑完再报一行汇总（成功/失败/跳过） |

所有消息都通过 `Reported` 事件回到 UI 线程，定时页顶部消息条展示。

## 五、界面

新增「定时」页（导航第 3 项，位于「任务」之后），一行一条计划，**行内直接编辑、改动即落盘**（无「编辑模式」，少一次点击）：

- 时间：时 / 分两个下拉框
- 周计划：一~日 7 个勾选框 + 文字摘要（「每天」「工作日」「一、三」）
- 开关：启用、强制启动（带 ToolTip 解释抢占语义）
- 操作：试跑（立即执行，不等时间到）、删除
- 绑定：配置组下拉 + 备注输入框 + 「下次触发：10-28 08:30 周三」
- 顶部工具条：调度状态（「调度运行中（每 20 秒检查一次）」）、配置组数量、「立即检查」、「新增定时」

截图冒烟（三条不同周计划的记录）确认无裁切 / 重叠 / 文字截断；空状态有引导文案；任务页无回归。

## 七、已知限制

1. **开机自启未做** —— 需注册表 `Run` 键或计划任务 + 静默启动参数，归 **P6.1 应用设置**（与「最小化到托盘」「关闭行为」一起做才完整）。
2. **TimerRunner 未单测** —— 它依赖 `InstanceWorkspace`（含 WPF 线程与真实引擎），在 App 层无测试宿主。已用「真引擎 + 调度器」的引擎层集成测试覆盖链路，App 层的胶水逻辑靠界面冒烟确认；若后续要补，需引入 `IExecutorHost` 之类的抽象。
3. **到点触发需要引擎已连接** —— 未连接时报错跳过，不会排队等待。MAA 同样如此（定时依赖已连接设备）。若需要「等连接后补跑」，留给 P6.2 的启动策略。
4. **无「整轮总时长上限」** —— 与 P5.3 一致的遗留，归 P6.2 运行设置。
